# How to continue the work

Guide for whoever picks up the project (a person or Claude Code). Setting up the game: `README.md`, section "Montar do zero". Method and vision: `PROJETO.md`. Everything known about the binary: `DESCOMPILACAO.md`. Each rewritten routine and its proofs: `ROTINAS.md`. Current state and next steps: `wiki/index.md`.

## Prerequisites

- The game **CM 01/02 3.9.68** installed in `jogo/` (it does not come with the repository). `patch_portatil.py` checks the MD5 of `cm0102.exe` and refuses any other version.
- The `cm0102-1080.exe` generated by `resolucao.py`: it is the one the test tools open.
- Python 3 with `pefile`, `capstone`, `psutil` and `Pillow`. Rust with the `i686-pc-windows-msvc` target (already configured in `rust/.cargo/config.toml`).

## The cycle of a batch

A batch has from 1 to 10 match engine routines (`match_eng.cpp`, `match_pl.cpp`, `match_day.cpp`), rewritten in `rust/src/motor.rs`.

1. **Choose.** `python candidatos.py` lists the routines that the real game executes (`docs/cobertura_motor.txt`) and that are not yet in Rust, ordered by what remains to be rewritten before them ("falta 0" = only calls already proven routines). `python candidatos.py 0x6c51e0` shows the real size and the pending calls. The top of the list has misaligned pieces of the map (broken addresses, few bytes): check with `desmonta.py`.
2. **Read.** Disassemble the whole routine (`desmonta.py` or capstone) and translate it instruction by instruction: signed bytes, 8- and 16-bit overflows, x87 floating point in double precision with the roundings to `float` at the same `fstp`s, and values that stay on the x87 stack without rounding. The constants are read from the `.rdata` itself (`f32_em`, `f64_em`). For large routines (hundreds of instructions), start from Ghidra's pseudocode (`python descompilar.py 0x...`, about 10 s per routine): it gets the loops, branches and stack variables right, including those read with an argument still pushed. But it hides what goes into `__ftol` and the roundings to `float`, and 16-bit code comes out as `CONCAT22`: the exact arithmetic comes from the disassembly.
3. **Write.** In `motor.rs`:
   - the routine, with the comment `/// { 0xENDERECO } (arquivo.cpp): o que faz`;
   - the `Prologo` (initial bytes copied to the trampoline: whole instructions and no relative jump; `prologos.py` checks);
   - the comparator `comparar_*` (runs original and Rust from the same state and compares the memory regions the routine may touch, plus the random draw state);
   - the entries in the `rust`, `comp` and `nomes` arrays of `instalar` (same order as `PROLOGOS`; `N` = total);
   - the case in the `autoteste` (synthetic inputs, including limits and edge cases, without falling into the original's error paths, which open a message box).
   - Internal calls to other routines go **through the game's address** (`transmute(0x...)`), so that in the comparison they pass through the already proven hooks.
4. **Prove** (the four criteria of `ROTINAS.md`):
   1. Self-test with mutations: write the list in `mutacoes/levaNN.py` (see the examples) and run `python mutacoes.py mutacoes\levaNN.py`. The base (200 thousand cases, about 3 minutes; `--base-completa` every 5 batches, about 35 minutes) must give 0 divergences and each mutation must be flagged (divergence or exception); the mutations run only the match engine with 200 thousand cases (`CM_AUTOTESTE=motor:200000`, about 1 second each). A mutation that passes with few cases: redo only it with `--casos 2000000` before concluding it is a gap. One that passes is either a gap in the test (fix the generator) or equivalent for the possible values (document why).
   2. Real game: `python simular.py --ate 2002-06-01 --motor sim --modo comparar --limite 900` (0 divergences in `jogo\ddraw.log`).
   3. Career: `python simular.py --ate 2002-06-01 --motor sim --modo rust --repetir 2`. The fingerprint must equal that of the original mode **of the same build** (`--modo original`; the set of hooks changes the stack garbage in both modes, and the reference number changes with it). In batches 50 to 52, `c76ad0ff6ce3daa6` with 2,357,335,216 random draws.
5. **Record.** Section for the batch in `ROTINAS.md` and in `ROTINAS.en.md`, translation of the new names in `glossario.py` (generates `GLOSSARIO.md` and `.en.md`), state in `wiki/index.md`, a line in `wiki/log.md`, commit and push.

## Known traps

- `fst dword` followed by a comparison: stores the rounded float but compares the double; reproduce by storing `v as f32` and comparing `v`. x87 `pow` (`_CIpow`): base in st1, exponent in st0 (the first one loaded is the base). 64-bit return (`edx:eax`): check which register the test uses.
- Globals that come from the database (club and competition ids) are 0 in the self-test, which runs before loading: give them distinct values during the test, otherwise mutations on them pass.
- Synthetic data that becomes a write address in the original routine (signed index, offset): restore the whole range it can reach, or use only real values. A game error box during the self-test shows on Lucas's screen (the self-test runs before the interface) and stalls the test without using the CPU. Do not interrupt `mutacoes.py` midway: `motor.rs` stays mutated.
- The comparison-mode fingerprint (`--modo comparar`) is not a criterion and changes between batches: both the original and the Rust version run, and a Rust version that calls hooked routines goes through their comparators. The criterion is zero divergences and the same fingerprint in the Rust and original careers. A new environment variable in `simular.py` shifts the heap and the reference fingerprint: reuse a CM_* with a value of the same length (e.g. `CM_OCULTO=2` for sound).
- Do not edit `motor.rs` while `mutacoes.py` runs: at the end it rewrites the file as it was at the start. Human-manager routines: the automatic career barely goes through them; the mutations need the synthetic self-test.
- A routine that hands error cases to the original: a mutation in the path that decides "it is an error" may vanish, because the original gets the result right. In the self-test, make the wrong path land on a different valid case (e.g. another valid person in the slot the mutation would read).
- Comparator of a routine that draws numbers: pass `crate::aleatorio::REGIOES_DO_ESTADO` to `lado_a_lado` and run the Rust side inside `sem_contar`; otherwise Rust draws from the state the original left. Stack variables read right after a `call` whose argument has not been popped yet (`add esp, 4` later): the offset is 4 less. A mutation that adds the same constant to every candidate does not change the pick (equivalent): replace it with one that changes the order.
- Self-test state shared by the whole case (tables A/B, globals, player blocks): save and restore it in the section itself. Invalid values may open an original routine's error box; with the game hidden, the test stops without using the CPU (`mutacoes.py` waits for the limit). Do not hook 4-byte getters (0x714d30 froze the game).
- What depends on the loaded database (club tactics at 0xde1d08, real people) does not run in the synthetic self-test, which happens before the database. For those routines: `mutacoes.py --jogo YYYY-MM-DD` (mutations in the real game in comparison mode). Mutating a path the real game hardly uses (the computer clubs' designated taker) proves nothing: aim at the common path.
- Self-test generator: one draw (`s.proximo()`) per value. Rotations of the same number (`rotate_left`) come out correlated and may never produce some cases (mutations pass because of that, not because they are equivalent). And keep the grid consistent: more than 11 players in a square corrupts the lists, and a comparator that reads pointers from them (0x6f46b0) crashes inside the DLL.
- Cargo does not recompile a `.rs` restored with an old timestamp: `mutacoes.py` updates the timestamp; by hand, check that "Compiling" appeared and that the DLL was copied to `jogo/`.
- In `asm!`, pointers that need to survive a call go in a preserved register (`edi`, `esi`), not in `eax`.
- The self-test generator may overwrite fields that other routines depend on (for example, the engine pointer at 0x19e of the player). A crash in the self-test is located through the linker map: `cargo rustc --release --lib -- -C link-arg=/MAP:target/ddraw.map`.
- Routines that record commentary events (0x6d6f70) or call 0x6cd330 use recording and replay: the original records the calls, and the Rust one checks against the recording without repeating the effects (`porta_6d6f70`, `GRAVANDO_6CD330`).
- One heavy test at a time (one game open at a time). `simular.py` uses `laboratorio.py`: lock `..\..\.laboratorio.lock` and memory watchdog. On Lucas's machine this exists because it is shared with other projects; elsewhere, the lock only serializes the tests.
- The tests always open the game windowed (`-windowed`, `CM_JANELA=960x540`) and back up and restore `game.cfg`.
- Before picking a routine, search for its address in every module (`grep 0x... rust/src/*.rs`): 0x417c10 (date copy) was already hooked by `data.rs`, and the repeated hook is refused ("bytes ... sao [e9 ...]"), leaving the original in the table at 0 (a jump to 0 in the self-test).
- The `byte()` helper in `motor.rs` returns `i8`: for `shr` (logical shift) or `movzx`/`xor eax,eax; mov al` (unsigned byte), write `byte(p, o) as u8`. In the 79th batch, a signed `byte(r, 0x4f) >> 4` made the self-test diverge right at the baseline.
- A self-test that hangs without using CPU is a game error box waiting for a click (in hidden mode no one sees it): in the 80th batch, a random mask without a sector bit sent the original 0x5b73a0 to the formation.cpp box. And when stopping a test chain midway, stop the chain's `bash` (TaskStop), not just the `python`: after a `;` the rest goes on (a career even started).
- A routine that returns only `al` or `ax`: declare the return as `u8`/`u16`, never `u32`. In the 81st batch, 0x5b2ae0 writes only `ax` on the +0x12d path and leaves the caller's garbage in the top of `eax`; with `u32` the self-test passed (the garbage was 0) and the real game reported 20 million false divergences.
- `fcomp` with NaN sets C0, C2 and C3: after `test ah,1` (or `0x41`), NaN counts as "less". In Rust, write `!(v >= limit)` instead of `v < limit`. In the 85th batch, the 2.2 power of a negative base gives NaN in both; the original zeroed the field and Rust kept the NaN (6,233 divergences in the real game). The function map says 8.5 KB for 0x6ec010, but it runs to 0x6eeca9 (~11 KB): check the end by the `ret`.
- Big x87 routines keep values alive on the stack between `_ftol` calls (which pop only the top): in 0x6eecb0, the squares of +0xe5 and +0xdd stay underneath and feed two or three following computations. Follow the stack instruction by instruction, without trusting Ghidra's pseudocode (which lost all of these computations). The size in the function map (1,730 bytes) was also wrong: the routine runs to the `ret 4` at 0x6f05c5.
- A short prologue ending in a `call rel32` or `jcc rel8`: list it in `RELATIVAS` (desvios.rs) with the instruction offset; the trampoline rebuilds it with the absolute target (jcc rel8 becomes rel32) and `prologos.py` accepts the instruction only there. Ghidra's pseudocode for 0x6b61e0 swapped the arguments of 0x48db80 and 0x5c6710 (they are thiscall with another `this`): the disassembly ruled.
- 0x6be120 passes its own argument slot as the 5th output of 0x6ce310 (`ebx` already holds the side); count the `push`es before each `lea [esp+x]` to find which local each pointer targets.
- A routine with side effects called by a ported one: a port at its prologue that records (this, arguments, answer) plus a snapshot of the regions the comparator asks for, taken after the call (`FITA_70DFD0`); the Rust copy writes the snapshot back instead of calling. The regions must cover everything the ported routine reads afterwards that the call can change.
- `mutacoes.py --jogo` read the previous run's `ddraw.log` when the memory guard refused the simulation ("0 s" mutations with the same divergence): it now deletes the log first, waits for memory and marks `SIMULACAO RECUSADA`. Distrust any mutation run that lasts a few seconds. Also, in comparison mode the `lado_a_lado` copies (allocated on every call) dominated a career with every league: routines called billions of times use `lado_a_lado_leve` (copies on the stack) or their own allocation-free comparator.
- Generic tape (`FITA`, `comparar_com_fita`, `chamar_gravando`): each recorded call keeps the routine, `this`, up to 5 arguments (compared with a mask: 0x6f09f0 and 0x6f46b0 read x and y as bytes), the answer and the snapshot of the regions. Only outer calls go in (`DENTRO` counts the depth: 0x70dfd0 and 0x6f09f0 move players internally). A comparator running inside an open recording (`gravando()`) only calls the original; without that guard it overwrites the outer tape. And every comparison zeroes the depth at the start (restoring it at the end): in normal play 0x6f5b80 runs inside 0x6f09f0, and without this its call never made it into the tape (baseline with `0 chamadas`).
- A routine with side effects that has its own comparator (0x6f5b80) and is called inside a recording goes into the tape as a unit (`chamar_gravando` in its comparator's `gravando()` branch): the calls it makes internally sit below the depth and stay out. Without this the Rust replica would run the original again (double effect). And the Rust copy runs after the whole original: everything it (or what it calls without recording) reads before a recorded call that the call changes must be in the regions. 0x6f09f0 decides and moves the other players internally, so the regions cover the engine from 0x215e to 0x8f00 (grid, the 40 players, ball). To find the cause, the tape divergence message carries the recorded × requested call, the differing regions and the draw trace of both runs (`aleatorio::rastrear`).
- Commentary (0x6d6f70) and ball pick-up (0x6f0630) inside a recording also go into the tape as units: the commentary port records only the first five arguments (the last two are −1 and 0 in the ported callers) and 0x6f0630's comparator uses `chamar_gravando` in its `gravando()` branch. And the tape also keeps the snapshot BEFORE each call: the replica checks it reached the same state before applying the after one. Without this, what the routine writes before calling (the action in +0x198) was wiped by the after snapshot and errors there went unnoticed (mutations `s_fica` and `s_formacao` from batch 95). Comparators with commentary (`comparar_com_comentarios_em`, `bola_fora`) also only run the original while a tape recording is open: otherwise their comments go to the outer tape and their own comparison gets lost.
- A routine with an out pointer on the tape (0x6fad40 writes into its caller's 3rd argument): the port returns the answer and the out byte together (`r | out << 8`) and the replica splits them. Pointers into the stack never go into the compared arguments (they change between runs). And nested comparison: a routine only called inside a recorded unit (the pass, inside 0x7109f0) was never compared, because its comparator only ran the original while the tape was open; mutation `p_2b` survived and showed it. Now, inside a unit (depth > 0, `gravando_no_topo()` false), a tape comparator stashes the outer tape, runs its own comparison and puts it back.
- Before porting, look the address up in motor.rs/data.rs: a repeated prologue makes the second hook be refused silently and the new routine never runs (0x6d3de0 and 0x6d3610 were already ported and got rewritten by mistake; every mutation survived). prologos.py now flags repeated addresses.
- A unit that reads or writes vectors on the caller's stack (outside the regions): use `chamar_gravando_vetores` in the port and `pedir_vetores` in the Rust copy before `chamar`, otherwise the copy gets empty outputs and the inputs are not checked.
- Joint batch run: `mutacoes/levaA_B.py` merges the lists (one base, one real game and one career for several batches; the divergence message names the routine). `mutacoes.py` stops when the base diverges (exit code 1) and the chain does not go on to the real game or the careers. In batch 116 the 1st base caught the candidate list: reserves come in from `vagas`, overwriting the rest of the sorted list.
- An uninitialized stack read blocks porting: 0x6dbc50 (kick-off team selection, match_man.cpp) in mode 2 never writes the short of the 1st extra place (stack +0x214 + 2·11: the loop writes the next index) and passes it to the pick (0x6e2000 → 0x6e2f20, which adds bonuses by its bits). The garbage is what the previous routine left on the private stack, different in Rust and original modes. Like 0x6d1cc0 (events with 4 uninitialized bytes), it stays original; the rest of match_man is in Rust. The recording port on 0x6dbc50 itself (and the Rust version of 0x6db500, which calls it) also stay out: in the simulation every detoured routine runs on the private stack, where the leftovers depend on the mode, and 0x6dbc50 started reading different garbage in Rust and original modes (careers a4eb4f4ca8d88100 × 28e69e02054b42a7; without both, 7cb2218eb00107c9 in both modes).
- **Comparison mode does not follow the original game's trajectory** (batch 125): each new comparison changes the stack garbage that original routines read later, and the compared game takes another course (in batch 124 it already split from the original on day 187). A new routine can thus lead the comparison into new situations, and a divergence in an old comparator calls for checking the comparator before the routine: in batch 125, `procurar_no_lado` replayed 0x6f5c30's answers without its effects (it takes the player off the list, changes +0x19/+0x2b); it now compares through the tape, with the list in the regions. What proves the routine is the career (Rust ×2 = original). Wiping the stack below the comparison on exit (experiment) makes comparing and just passing through give the same game.
- **The engine is 0xf63b bytes, not 0xf5f8** (batch 126): the game allocates it with `new(0xf63b)` (0x6b4a48, 0x6b52fe, 0x6b5bc6, 0x6b6b00, 0x84c33e). The comparisons used (m, 0xf5f8) as "the whole engine" and left out the end of side 1's block (+0xf5f2, 0x36 bytes: the fouls at +0xf5ff) and the fields up to +0xf63a. The tackle's replay saw the fouls already counted by the original (the punishment comes later) and the referee's decision (0x6e9820, which uses the fouls in its strictness) changed. All of them now use the `MOTOR` constant. Found by measuring the state in both runs field by field; before that, engine, players, RNG and FPU (control word 0x27f) were equal.
- **Mutations by measured branches** (batch 127): the Rust copy marks branches with `crate::comparacao::ramo("name")` (counted in the log, "ramo <name>: N" at each power of 2) and the mutation list can name each one's branch (fourth field). `mutacoes.py` reads the base and skips the mutation whose branch did not run, logging the measured gap instead of spending the run. **Comparison mode 37% lighter** (batch 127): the snapshots reuse buffers (allocating 63 KB per snapshot was most of the time) and the scoreboard milestone no longer divides at every comparison; measured by the game's CPU time (1,121 s → 710 s to 2001-10-01, identical game). Wall-clock time varies ~20% with machine load; compare versions by CPU (`medir_cpu`). Other attempts (a `HashMap` pool, checking without copying) were slower.
- Narration with a 7th argument other than 0 (129th batch): in the copies with `chamar`, a7 goes in the code's high bits (`codigo | a7 << 16`, signed), and `despachar_dividida` unpacks it. The 0x6d6f70 port only records a7 on the tape with `GRAVAR_A7` on (the routine's comparison turns it on and uses mask 0xffffff on the code); elsewhere the 0xffff mask ignores it.
- **Mutations through the career, with the match fingerprint** (2026-10-13, Lucas's proposal): `mutacoes.py --carreira 2002-06-01 --confirmar YYYY-MM-DD`. Each mutation runs the automatic career in Rust mode (~2.5 min, no comparison) and is caught if the fingerprint changes. The fingerprint gained a match part: the hash of each match engine when freed (0xf640 bytes at HeapFree, the CRT-rounded `new(0xf63b)`), chained — 19,548 matches to 2002-06-01, equal in Rust and the original (`0ac236ae64589294`). Without it, batch 128's `r_penalti` (1 point on +0x35) escaped; with it batch 128 got 12 of 12 in ~28 min (vs ~2.4 h in compare mode). Whatever escapes the career is rerun in the comparing game (`--confirmar`). The career does not say where it diverged: to locate it, `--jogo`. Reference careers now check both fingerprints.
- **Daily database fingerprint** (batch 130): the career gains a third fingerprint, `banco`: at the first draw of each day, the hash of the database blocks (those pointed to by the pointer table 0xae2300..0xae2400 — people, clubs... —, the table at [[0xb67a44]] and the GlobalAlloc block; 11 blocks, ~15 MB), chained. Rust and the original are equal on every day (518 to 2002-06-01, `923a4e0edd9f2e09`; 883 to 2003-06-01 with seed 777). The whole heap is no good: it mixes the interface (image buffers, screens), which the game draws at moments that depend on speed and differs between modes without changing the game (one dword of a messages screen in 2003, the whole day in the diary). The daily hash catches a change that is later erased (batch 130's `e_1e_tecnico`); what is undone within the same day (the [[0xb67a44]] table goes back to 5000) only a side-by-side comparison would see. To find what differs: `jogo\heap_fim.txt` containing a path dumps the heap at the end (a file, not an environment variable, which would shift the heap and change the career); with `CM_RASTRO`, the day's snapshot.
- **Post-match comparison through the tape** (2026-10-14): the database routines full of effects (0x6b74a0, 0x6b6cc0, 0x6b79a0) have a side-by-side comparison with a tape: 15 ports (`PROLOGOS_POS`) on the database routines with effects they call, which only record with `GRAVAR_POS` on and pass through for the rest of the game (all return edx:eax; none returns floating point). The lookups that look pure but reach 0x68d0d0 (allocates and records) — 0x6b7cf0, 0x600a50, 0x53b900, 0x4cf5f0, 0x7c3a40 — also become units: their comparators record themselves when called inside a post-match comparison (`gravando_pos`). In the copies, these calls go through `chamar` (closures with the same names, over a `RefCell`). It caught `c_57`, `c_ficha` and `e_0a_sorteio`, which escaped the career.
- **The tape checks the draws** (2026-10-14): besides the regions and the call sequence, the list of draws (request, result) of the original and the copy must match. `sortear(6)` instead of `sortear(5)` with the same result changed neither memory nor the generator. Draws inside a recorded unit stay out of the original's trace (`aleatorio::pausar_rastro` in `chamar_gravando` and `chamar_gravando_vetores`): the copy receives the result and does not redo them.
- **Stack garbage in the contest (0x6c9cd0)** (2026-10-14, found in Lucas's comparing session): the referee's decision (0x6e9820) returns before writing the advantage on several paths (no engine, game stopped, impatient referee, hard foul in the box). The original then reads whatever was left on the stack (the contest's \[esp+0x16\]); with +0x8ebb on (match watched with commentary) and the winner in the box, that garbage decides narration 0x2168 and one draw, and the match takes another path. **Lucas's decision:** the Rust copy uses 0 (marker `SEM_RESPOSTA` before the call; branch `disputa vantagem sem resposta`, 2048+ times to 2002-06-01). In comparison, a divergence with an unanswered advantage is counted separately (`LIXO_DE_PILHA` in the log), not as a divergence. In automatic careers +0x8ebb is never on and there is no effect.
- **Test folder and `tracar_lance` on the original** (2026-10-15): automatic tests (`simular.py`, `mutacoes.py`, the chain) run in `jogo_testes/` (a copy of `jogo/`, outside git), because the automatic career reads the folder (saves, `hall_of_fame.bin`) and Lucas's games in `jogo/` moved the reference. In the new folder (with the save and hall of fame from Lucas's 2nd session) the Rust career split from the original on 2002-01-12 already in batch 134: a binary search over the 301 routines (`SEM_ROTINAS`, now through the pass-through hook) pointed only to 0x6ccb60 `tracar_lance`, and a probe (original and copy tracing the same play without running anything) gave the same squares and arguments — what changes is the stack leftover for an original routine called afterwards, which reads garbage. It went into `SO_NA_COMPARACAO`: outside comparison it runs the original (through pass-through); in comparison the copy is still checked. New reference: 2,368,855,859 draws to 2002-06-01, fingerprint 459815f5e0dca92b, matches 9ad4f994099c32e2, database c8c977301cbf96ba. The garbage reader is not identified yet.
- **Career sensitive to code shape on 2002-01-12** (2026-10-15): moving 0x6f5c30's punished-foul part into a function (identical logic, checked line by line; 0 divergences comparing) changed the Rust career (318bbdd46710d74c against 459815f5e0dca92b), splitting on 2002-01-12 — the same day as batch 135's `tracar_lance`. Dirtying 4 to 64 KB of stack before each original call in that part, or after it, changes nothing; moving the branch marker neither; with `CM_RASTRO` on the new version matches again. It is neither stack garbage nor logic: something in the game that day depends on memory layout (heap or timing). 0x6f5c30 keeps the inline copy (the shared function only serves the shot). When a change with no logical effect moves the career on 2002-01-12, it is this case: investigate that day's event before touching the routine.
- **Determinized original** (2026-10-15, approved by Lucas): an original routine that reads a local variable with no value goes into `ZERADAS` (`motor.rs`); the `desvios::desviar_zerando` hook zeroes 8 KB of stack below the entry in every mode (with a Rust copy its hook zeroes too; in comparison, `zerar_pilha()` before calling the original). First ones: 0x6dbc50, 0x6d1cc0, 0x6beeb0; the reference career did not change (459815f5e0dca92b). Batch 212 (2026-10-22) added 0x84be20 (simulated_stats.cpp): it builds the simulated match record on the stack and never writes the word +0x38, which the quick simulation 0x6beeb0 reads (extra time and penalty rules); the garbage there was left over by 0x7c6bf0's bsearch. **The same day the zeroing was undone:** with +0x38 at zero the quick simulation leaves draws without a decider, a path the real game hardly ever takes, and the 8-league career (the broad one) split Rust and original (bisection over the history: commit 4af06b2). Zeroing is only faithful when zero is a value the game also produces. Instead 0x7c6bf0 was **switched off** (`DESLIGADAS` in `motor.rs`: no hook in any mode, the original runs on the game stack and leaves the usual residue) until the copy can reproduce that residue. Lesson: when a hook changes the residue an original uses, switching the hook off is the safe retreat; zeroing is for garbage that really varies. References after that: career b28542870027e432, real game comparing 963cea289f055ac3 (the one before batch 212), broad 9ee2b5acf52a3bcb (the one from 10/19). The references live in `gen_docs.py` (`REF_JOGO`/`REF_CARREIRA`) and the broad career (Rust = original) joins the proof before they change. Before porting such a routine: a probe (how often the garbage shows up, whether zeroing changes anything) and a mutation that touches the zeroed value, to prove the comparison sees it (in batch 139, `f_lixo_evento`).
- **Comparator nested in the tape** (batch 140): a routine compared through the tape calls, in the original, routines whose comparators do their own side-by-side (0x6c0c60, the choices 0x6c2750...). `lado_a_lado` runs the Rust side with the draw trace paused (`aleatorio::pausar_rastro`); without it, the nested copy's draws go into the original's trace and the tape reports "different draws" with equal memory.
- **Comparison inside a unit** (batch 142): a routine that only runs as a unit of other tapes (called by 0x6cd770, 0x6fad40...) is never compared if its comparator only records the unit. The comparator records the unit for the outer tape and, inside it, runs its own comparison (`comparar_com_fita` nests: it saves the outer tape and level). ## Save proof

For the batches of the save block (`docs/MAPA_SAVE.en.md` §4), which the automatic career does not exercise: `python engenharia-reversa/prova_save.py`.

1. **Write:** the quick start (`quick_start.cfg` → `PROVA.cfg`) writes `qstart\PROVA.qst` in `jogo_testes`, once in the original and once in Rust, with a fixed seed and the DLL's simulation mode. Compression is bit 0x8000 of the `game.cfg` dword +4 (= `[0xae3138]+4`): **set = type 3** (uncompressed), **clear = type 4** (RLE). `--tipo 4` (the default) clears the bit only during the proof; `game.cfg` is restored at the end.
2. **Compare:** the two `.qst` files (in `%TEMP%\cm0102_prova_save`) byte by byte; if they differ, the container item and the offset inside the decompressed item. Ignored (`IGNORAR`): the play time and the summary's `time()` in `general.dat` (+0xf70, +0xf74; fixed in simulation mode, but not game state). `--comparar A B` runs only this step.
**Measured on 2026-10-23:** the tool writes both type-4 `.qst` files in ~5 s each, but they never come out identical. In the same mode, two runs differ in 13 bytes of `general.dat` (pointer garbage the game writes uninitialised, changing on every run). Between original and Rust there are also 161 bytes of `staff history.tmp` (different heap residue). So the proof of a save batch compares **the same DLL, in the same mode, with and without the batch routines**: two base writes teach the bytes that vary on their own (`--variaveis BASE1 BASE2`) and the write with the batch must be EQUAL outside them (`--comparar BASE BATCH --variaveis BASE1 BASE2`). Rust against Rust with the mask: EQUAL.

3. **Load:** only with `--sav <save with a manager on holiday>`. `-load` of a `.qst` stops at the manager name screen (no human manager, 0x838d10 → 0x820d40), and `-load` is read before `auto_setup.cfg` (0x81bdb1): the automatic career is not created. The `.sav` with a manager on holiday is made once by Lucas (automatic career, Save menu). The proof loads a copy in both modes up to `--ate` (default 2001-09-01) and compares the `simular.py` fingerprint.

Output in short lines (`gravar rust: ...`, `comparar: IGUAL` or `DIFERENTE item N name +0x...`, `carregar original: ...`, `prova do save: OK`), exit code 0 only if everything matches. `--so-gravar` skips the load. The bench (lock, watchdog, `game.cfg`, `*.tmp`) is the one from `simular.py` (`bancada`, `rodar`).
