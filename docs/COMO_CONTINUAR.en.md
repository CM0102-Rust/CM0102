# How to continue the work

Guide for whoever picks up the project (a person or Claude Code). Setting up the game: `README.md`, section "Montar do zero". Method and vision: `PROJETO.md`. Everything known about the binary: `DESCOMPILACAO.md`. Each rewritten routine and its proofs: `ROTINAS.md`. Current state and next steps: `wiki/index.md`.

## Prerequisites

- The game **CM 01/02 3.9.68** installed in `jogo/` (it does not come with the repository). `patch_portatil.py` checks the MD5 of `cm0102.exe` and refuses any other version.
- The `cm0102-1080.exe` generated by `resolucao.py`: it is the one the test tools open.
- Python 3 with `pefile`, `capstone`, `psutil` and `Pillow`. Rust with the `i686-pc-windows-msvc` target (already configured in `rust/.cargo/config.toml`).

## The cycle of a batch

A batch has from 1 to 10 match engine routines (`match_eng.cpp`, `match_pl.cpp`, `match_day.cpp`), rewritten in `rust/src/motor.rs`.

1. **Choose.** `python candidatos.py` lists the routines that the real game executes (`docs/cobertura_motor.txt`) and that are not yet in Rust, ordered by what remains to be rewritten before them ("falta 0" = only calls already proven routines). `python candidatos.py 0x6c51e0` shows the real size and the pending calls. The top of the list has misaligned pieces of the map (broken addresses, few bytes): check with `desmonta.py`.
2. **Read.** Disassemble the whole routine (`desmonta.py` or capstone) and translate it instruction by instruction: signed bytes, 8- and 16-bit overflows, x87 floating point in double precision with the roundings to `float` at the same `fstp`s, and values that stay on the x87 stack without rounding. The constants are read from the `.rdata` itself (`f32_em`, `f64_em`). For large routines (hundreds of instructions), start from Ghidra's pseudocode (`python descompilar.py 0x...`, about 10 s per routine): it gets the loops, branches and stack variables right, including those read with an argument still pushed. But it hides what goes into `__ftol` and the roundings to `float`, and 16-bit code comes out as `CONCAT22`: the exact arithmetic comes from the disassembly.
3. **Write.** In `motor.rs`:
   - the routine, with the comment `/// { 0xENDERECO } (arquivo.cpp): o que faz`;
   - the `Prologo` (initial bytes copied to the trampoline: whole instructions and no relative jump; `prologos.py` checks);
   - the comparator `comparar_*` (runs original and Rust from the same state and compares the memory regions the routine may touch, plus the random draw state);
   - the entries in the `rust`, `comp` and `nomes` arrays of `instalar` (same order as `PROLOGOS`; `N` = total);
   - the case in the `autoteste` (synthetic inputs, including limits and edge cases, without falling into the original's error paths, which open a message box).
   - Internal calls to other routines go **through the game's address** (`transmute(0x...)`), so that in the comparison they pass through the already proven hooks.
4. **Prove** (the four criteria of `ROTINAS.md`):
   1. Self-test with mutations: write the list in `mutacoes/levaNN.py` (see the examples) and run `python mutacoes.py mutacoes\levaNN.py`. The base (200 thousand cases, about 3 minutes; `--base-completa` every 5 batches, about 35 minutes) must give 0 divergences and each mutation must be flagged (divergence or exception); the mutations run only the match engine with 200 thousand cases (`CM_AUTOTESTE=motor:200000`, about 1 second each). A mutation that passes with few cases: redo only it with `--casos 2000000` before concluding it is a gap. One that passes is either a gap in the test (fix the generator) or equivalent for the possible values (document why).
   2. Real game: `python simular.py --ate 2002-06-01 --motor sim --modo comparar --limite 900` (0 divergences in `jogo\ddraw.log`).
   3. Career: `python simular.py --ate 2002-06-01 --motor sim --modo rust --repetir 2`. The fingerprint must equal that of the original mode **of the same build** (`--modo original`; the set of hooks changes the stack garbage in both modes, and the reference number changes with it). In batches 50 to 52, `c76ad0ff6ce3daa6` with 2,357,335,216 random draws.
5. **Record.** Section for the batch in `ROTINAS.md` and in `ROTINAS.en.md`, translation of the new names in `glossario.py` (generates `GLOSSARIO.md` and `.en.md`), state in `wiki/index.md`, a line in `wiki/log.md`, commit and push.

## Known traps

- `fst dword` followed by a comparison: stores the rounded float but compares the double; reproduce by storing `v as f32` and comparing `v`. x87 `pow` (`_CIpow`): base in st1, exponent in st0 (the first one loaded is the base). 64-bit return (`edx:eax`): check which register the test uses.
- Globals that come from the database (club and competition ids) are 0 in the self-test, which runs before loading: give them distinct values during the test, otherwise mutations on them pass.
- Synthetic data that becomes a write address in the original routine (signed index, offset): restore the whole range it can reach, or use only real values. A game error box during the self-test shows on Lucas's screen (the self-test runs before the interface) and stalls the test without using the CPU. Do not interrupt `mutacoes.py` midway: `motor.rs` stays mutated.
- The comparison-mode fingerprint (`--modo comparar`) is not a criterion and changes between batches: both the original and the Rust version run, and a Rust version that calls hooked routines goes through their comparators. The criterion is zero divergences and the same fingerprint in the Rust and original careers. A new environment variable in `simular.py` shifts the heap and the reference fingerprint: reuse a CM_* with a value of the same length (e.g. `CM_OCULTO=2` for sound).
- Do not edit `motor.rs` while `mutacoes.py` runs: at the end it rewrites the file as it was at the start. Human-manager routines: the automatic career barely goes through them; the mutations need the synthetic self-test.
- A routine that hands error cases to the original: a mutation in the path that decides "it is an error" may vanish, because the original gets the result right. In the self-test, make the wrong path land on a different valid case (e.g. another valid person in the slot the mutation would read).
- Comparator of a routine that draws numbers: pass `crate::aleatorio::REGIOES_DO_ESTADO` to `lado_a_lado` and run the Rust side inside `sem_contar`; otherwise Rust draws from the state the original left. Stack variables read right after a `call` whose argument has not been popped yet (`add esp, 4` later): the offset is 4 less. A mutation that adds the same constant to every candidate does not change the pick (equivalent): replace it with one that changes the order.
- Self-test state shared by the whole case (tables A/B, globals, player blocks): save and restore it in the section itself. Invalid values may open an original routine's error box; with the game hidden, the test stops without using the CPU (`mutacoes.py` waits for the limit). Do not hook 4-byte getters (0x714d30 froze the game).
- What depends on the loaded database (club tactics at 0xde1d08, real people) does not run in the synthetic self-test, which happens before the database. For those routines: `mutacoes.py --jogo YYYY-MM-DD` (mutations in the real game in comparison mode). Mutating a path the real game hardly uses (the computer clubs' designated taker) proves nothing: aim at the common path.
- Self-test generator: one draw (`s.proximo()`) per value. Rotations of the same number (`rotate_left`) come out correlated and may never produce some cases (mutations pass because of that, not because they are equivalent). And keep the grid consistent: more than 11 players in a square corrupts the lists, and a comparator that reads pointers from them (0x6f46b0) crashes inside the DLL.
- Cargo does not recompile a `.rs` restored with an old timestamp: `mutacoes.py` updates the timestamp; by hand, check that "Compiling" appeared and that the DLL was copied to `jogo/`.
- In `asm!`, pointers that need to survive a call go in a preserved register (`edi`, `esi`), not in `eax`.
- The self-test generator may overwrite fields that other routines depend on (for example, the engine pointer at 0x19e of the player). A crash in the self-test is located through the linker map: `cargo rustc --release --lib -- -C link-arg=/MAP:target/ddraw.map`.
- Routines that record commentary events (0x6d6f70) or call 0x6cd330 use recording and replay: the original records the calls, and the Rust one checks against the recording without repeating the effects (`porta_6d6f70`, `GRAVANDO_6CD330`).
- One heavy test at a time (one game open at a time). `simular.py` uses `laboratorio.py`: lock `..\..\.laboratorio.lock` and memory watchdog. On Lucas's machine this exists because it is shared with other projects; elsewhere, the lock only serializes the tests.
- The tests always open the game windowed (`-windowed`, `CM_JANELA=960x540`) and back up and restore `game.cfg`.
- Before picking a routine, search for its address in every module (`grep 0x... rust/src/*.rs`): 0x417c10 (date copy) was already hooked by `data.rs`, and the repeated hook is refused ("bytes ... sao [e9 ...]"), leaving the original in the table at 0 (a jump to 0 in the self-test).
- The `byte()` helper in `motor.rs` returns `i8`: for `shr` (logical shift) or `movzx`/`xor eax,eax; mov al` (unsigned byte), write `byte(p, o) as u8`. In the 79th batch, a signed `byte(r, 0x4f) >> 4` made the self-test diverge right at the baseline.
- A self-test that hangs without using CPU is a game error box waiting for a click (in hidden mode no one sees it): in the 80th batch, a random mask without a sector bit sent the original 0x5b73a0 to the formation.cpp box. And when stopping a test chain midway, stop the chain's `bash` (TaskStop), not just the `python`: after a `;` the rest goes on (a career even started).
- A routine that returns only `al` or `ax`: declare the return as `u8`/`u16`, never `u32`. In the 81st batch, 0x5b2ae0 writes only `ax` on the +0x12d path and leaves the caller's garbage in the top of `eax`; with `u32` the self-test passed (the garbage was 0) and the real game reported 20 million false divergences.
- `fcomp` with NaN sets C0, C2 and C3: after `test ah,1` (or `0x41`), NaN counts as "less". In Rust, write `!(v >= limit)` instead of `v < limit`. In the 85th batch, the 2.2 power of a negative base gives NaN in both; the original zeroed the field and Rust kept the NaN (6,233 divergences in the real game). The function map says 8.5 KB for 0x6ec010, but it runs to 0x6eeca9 (~11 KB): check the end by the `ret`.
- Big x87 routines keep values alive on the stack between `_ftol` calls (which pop only the top): in 0x6eecb0, the squares of +0xe5 and +0xdd stay underneath and feed two or three following computations. Follow the stack instruction by instruction, without trusting Ghidra's pseudocode (which lost all of these computations). The size in the function map (1,730 bytes) was also wrong: the routine runs to the `ret 4` at 0x6f05c5.
- A short prologue ending in a `call rel32` or `jcc rel8`: list it in `RELATIVAS` (desvios.rs) with the instruction offset; the trampoline rebuilds it with the absolute target (jcc rel8 becomes rel32) and `prologos.py` accepts the instruction only there. Ghidra's pseudocode for 0x6b61e0 swapped the arguments of 0x48db80 and 0x5c6710 (they are thiscall with another `this`): the disassembly ruled.
