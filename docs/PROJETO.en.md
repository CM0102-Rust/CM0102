# CM 01/02 in Rust: what the project is, where we are and where we are going

*Vision document. The day-to-day state is in `wiki/index.md`; what is known about the binary, in `DESCOMPILACAO.md`; each rewritten routine, in `ROTINAS.md`.*

## 1. What we are doing

**Rewriting Championship Manager 01/02 (version 3.9.68) in Rust, from inside the game itself, without it ever ceasing to work.**

It is not a remake nor an "inspiration": it is the same simulation, with the same rules, the same numbers and the same random draws, rebuilt routine by routine from the original executable. The goal is that, starting from the same saved game and the same seed, the Rust version produces **exactly** the same career as the original, bit for bit.

Only once the reconstruction is faithful comes the second half: modernizing what the original game did not do (resolution, fonts, interface, current rules and leagues), on top of a base we fully understand.

## 2. Principles

1. **Fidelity above all.** Each rewritten routine must give the same result as the original, including floating-point roundings, 8- and 16-bit overflows and even stack garbage that the original passes along, when that affects the result.
2. **The game stays playable the whole time.** No "stop everything to rewrite". The Rust version comes in as a DLL that the original executable loads; each rewritten routine replaces the original through a *hook*. At any moment the game can be played, and the routines not yet rewritten keep running as always.
3. **Proof, not trust.** No routine is considered done because it "looks right". It goes through tests that compare it with the original and, before that, we prove that the tests themselves can catch errors.
4. **The originals are never modified.** Fixes and adaptations go into tool-generated copies, which checks the original's signature before touching anything.
5. **Nothing from the game in the repository.** No executables, no data, no raw decompiled code. The repository holds only the tools, the new code and the documentation.

## 3. How it works inside

```
cm0102.exe (original, untouched)
   │  loads
   ▼
ddraw.dll  ← our Rust core
   ├── our own video (replaces DirectDraw: window, 1920×1080, scaling)
   ├── hooks: at the start of each rewritten routine, a jump to the Rust version
   ├── reproducible simulation (clock, memory, disk and random draws under control)
   └── rewritten routines (random draws, dates, match engine...)
```

Each rewritten routine can run in three modes:

- **Rust:** the new version replaces the original (the normal mode).
- **Original:** only the original runs (reference).
- **Comparison:** both run side by side, from the same state, and any difference is logged.

## 4. How we prove a routine is right

Each batch of routines goes through four proofs:

1. **Self-test:** billions of synthetic inputs, including edge cases, on which original and Rust must give the same result.
2. **Mutations:** we deliberately alter the Rust version (a threshold, a sign, a constant) and confirm that the self-test flags it. If a mutation passes, either it is provably equivalent (and that is documented) or the test had a gap, which we fix.
3. **Comparison in the real game:** an automatic career runs with both versions side by side (10 billion comparisons per run), with no divergence at all.
4. **Full career:** the same career, with the match engine on, up to 2002-06-01, in Rust and in the original. The final "fingerprint" (2,356,606,166 random draws and the generator state) must be identical.

Routines that call others with side effects (for example, the match commentary) are compared by **recording and replay**: the original runs and each internal call is recorded; the Rust version is checked against that recording, without repeating the effects.

## 5. What has been done

### Stage 0: survey (2026-10-05)
- Reverse-engineering tools: reading the executable, strings, references, disassembly.
- **Map of the executable:** 11,314 functions, most of them linked to the original source file (`match_eng.cpp`, `Date.cpp`...).
- Formats of the data files.

### Stage 1: playable game, modern on the outside (2026-10-05)
- "Portable" executables (not requiring the CD), generated by a tool.
- Our own video layer in place of DirectDraw: resizable window, native 1920×1080, remembered position.

### Stage 2: reproducible test bench (2026-10-05 and 2026-10-06)
- The game was made **deterministic** inside the simulation: clock, memory (fixed allocator), disk, drives and all Windows calls under control.
- Automatic "holiday" career, with no screen and no clicks.
- **Long proof:** ten seasons with Rust and original identical.
- The first routines in Rust: the random draw generator and the game dates.

### Stage 3: match engine (2026-10-06 to 2026-10-17) and simulation, in progress
- **272 batches, 1658 routines** rewritten, bottom-up: from accessors and calculations to tactical decisions, ball possession, refereeing (fouls, cards, offside), statistics, player movement, ball control, commentary and, as feasibility proofs, the **shot-on-goal value** and the **team strength** (5 KB routines).
- New infrastructure: hook verification (`prologos.py`), a recording gate for the commentary and replay of internal calls.
- The match engine (screens aside) reached 100% on 2026-10-17; since then the batches go through the simulation (`candidatos.py --simulacao`) and, from batch 180, through the match screens (`match_screens.cpp`).

## 6. Where we are going

1. **Close the engine with the match screens.** The screens build a display list (the screen manager's `Display`), compared as data; the proofs are Lucas's game in Rust mode and comparing.
2. **The rest of the simulation:** the match day, competitions, tables, transfers, finances, contracts, injuries, news. Same method: routine by routine, proven against the original. **Order (Lucas, 2026-10-22):** close `match_screens.cpp` and `match_day.cpp` (6 functions left); then map and port, in blocks, the **save** (`zipdir.cpp`, the container with RLE, and `Setup.cpp`, save/load; reference: CM3SaveEditor, already in Rust), the **database** (`Database.cpp`, `index.cpp`: reading `Data/*.dat`) and finally the **competitions** (~180 classes in `comp/`: 87 leagues, 60 cups, European, intercontinental and World Cup, with the structure written in the code). Each block opens fronts in the sibling tools (editor, CMRTE, Save Game Editor); competitions in Rust are the path for the editor to change the structure (item 8).
3. **The interface (decided on 2026-10-19: hybrid approach).** Translate the interface base and each screen's logic, rewrite the presentation over the base checked pixel by pixel, and only then modernise.
4. **Independence from the executable.** With the whole simulation in Rust, the core becomes a library of its own (64-bit), which runs without `cm0102.exe`.
5. **Modernization.** Resolution and fonts, pictures fitted to the screen and, on top of the faithful base, changes to rules and realism.
6. **New ways of seeing the game.** The engine already computes the match on a board (positions of each player and of the ball at each play); with it in Rust, it becomes possible to draw the match (2D, "button football") in a modern interface (Unity, Godot or another), reading the engine.
7. **Challenge mode (Lucas's idea, 2026-10-08).** Several players, each at home, play the same career (e.g. "Flamengo on seed 1") and compare results; whoever does best, in theory, plays best. The simulation is already reproducible (same seed and same decisions give the same result), but the same seed only guarantees the same starting world: the game uses a single queue of draws, and any different decision changes how many draws are spent, shifting all the luck from then on (including other clubs' matches). To compare skill fairly, with the engine fully in Rust:
   - **a seed per event**, derived from seed + date + home + away (and the same for injuries, transfers, youth players): other matches come out the same for everyone and the player's own match starts with the same luck, so the difference comes from the decisions;
   - **against save reloading**: the player sends the seed and the decision log, and a verifier replays the career and confirms the result (possible precisely because the simulation is deterministic);
   - **same conditions**: same database (`Data/`), same version and same options (loaded leagues, match detail);
   - only with the engine 100% in Rust: in the original exe, stack garbage influences the results (see ROTINAS, note on the career fingerprint).
   It is a separate mode: it breaks fidelity to the original on purpose and does not replace the identical game.
8. **After the 1:1 game: the editors inside the project (Lucas's roadmap, 2026-10-21).** All of this comes only after the game is entirely in Rust and identical to the original.
   - **CMRTE inside the game.** A button turns on editing on the screen itself, like FM's in-game editor. The base is the sibling project `D:\Sistemas\CMRTE` (CMRTE v0.1.11 decompiled: Rust core done, proven by the original's gold output and by mutations). Inside the game there is no need to read and write another process's memory: editing touches the structures the game uses directly.
   - **The official editor rebuilt.** Decompile the database editor that ships with the game and rebuild it along the lines of the Elifoot II Bombado editor (`D:\Sistemas\Elifoot II\bombado\editor`): a core with no screen (database, entities, validation, patch) and the window on top (Tauri, HTML/CSS/JS without Node); the database only stores what passes validation, and changes can go out as a patch (the difference from the source database).
   - **The save editor in the same editor.** The Save Game Editor's logic is already decompiled and in Rust in the sibling project `D:\Sistemas\CM3SaveEditor` (Graeme Kelly's `SaveGame_Editor.exe` v4.0; `cm3sav` core, opening and saving byte for byte like the original, validator and batch editing). It goes into the new editor: one program for both the database and the save.
   - **Corrupted saves, solved at the root.** Understand why saves end up with broken ids (duplicated clubs and people, which today only the save editor's "repair" fixes) and fix it in the game, so the repair is no longer needed. Leads already gathered from the old forum threads (`ENDERECOS_COMUNIDADE.en.md`, old threads section): editors used together, nationality, job or retirement changed by an editor, two exes in the same folder sharing the `.tmp` files, power cuts while saving, Windows VirtualStore.
9. **Suggestions across the projects (to discuss).**
   - **A shared data core.** Today the database and save formats are described in three places (this project, CM3SaveEditor and CMRTE). A Rust library with just the formats, used by the game, the editor and on-screen editing, avoids three versions of the same structures.
   - **The validator in the game.** The save editor's validator can run in the game itself when saving and loading: the problem is reported (and, when safe, fixed) the moment it appears, not years later.
   - **The siblings' oracles in the chain.** CMRTE's gold output and `cm3sav`'s byte-for-byte oracle can join the tests here, proving the game and the editors together.
   - **The extended save together with the editor.** The format to go past 4 GB should be born together with the editor, which needs to read both formats.
   - **Rules as data.** What today can only be changed by patching bytes in the exe (start year, foreigner limits, substitutions, transfer windows, playable leagues; see the old forum threads) becomes configuration editable in the editor, like the rules as data in Elifoot II Bombado.
   - **Other platforms.** With the whole game in Rust and its own window, the Elifoot II path applies here: Linux, then Mac.

## 7. Risks and open decisions

- **Pace:** from 2 to 10 routines per batch and from 30 to 60 minutes of tests per batch. The engine will be done in a few dozen more batches; the whole game, with the same method, is months of work.
- **Shared machine:** the heavy tests respect a lock between sessions and a memory watchdog (there was a driver leak that froze the PC).
- **Interface:** decided on 2026-10-19 (hybrid approach, section 6.3); the match screens are already in Rust and being tested.
- **Large routines:** the method scales. The shot value (5.2 KB) and the team strength (5.1 KB, full of internal calls with effects) matched the original on the first attempt; the problems were only in the test infrastructure.
