# CM 01/02 3.9.68: what is known about the binary

Addresses as VA (base 0x400000), referring to `cm0102.exe` unless stated otherwise.

## 1. The executables

| | `cm0102.exe` | `cm0102_GDI.exe` |
|---|---|---|
| MD5 | `ed0cb3bc9bcc8ac3964dad52f6007cb8` | `0ece18564ace3012e67912c9f8a30000` |
| Compiled | 2002-11-21 13:12 UTC | 2002-11-21 17:19 UTC |
| Video | DirectDraw (`DDRAW.dll`) | GDI (`StretchDIBits`), no DirectDraw |

- Compiler: **Visual C++ 6** (linker 6.0), C++ with static CRT and SEH exceptions (`fs:[0]` in the prologue).
- Sections: `.text` 0x401000–0x9660e5 (code, ~5.4 MB); `.rdata` 0x967000; `.data` 0x987000 (0x45d63c in memory, only 0x153000 in the file); `.rsrc` 0xde5000. In `.text`, `.rdata` and `.data` the file offset is VA − 0x400000.
- Interface: a single window (`CreateWindowExA`, class `"main"`), everything else drawn by the game itself. There are no Windows controls. This makes it possible to rewrite the interface pixel by pixel.
- Other dependencies: `DSOUND` (sound), `WSOCK32` (network play), `WINSPOOL`/`comdlg32` (printing), `ADVAPI32` (only reads the registry).

## 3. Fixes in the portable exes

Generated by `engenharia-reversa/patch_portatil.py`, which checks the MD5 and locates everything by pattern (works for both exes).

1. **CD.** The check was copied into **33 places** in the code. Each copy walks the drives (`GetLogicalDriveStringsA`), looks for `<CD drive>\cm0102.exe` (`_findfirst`) and, if it does not find it, shows "Please insert the CM01/02 CD" and repeats. Fix: the loop runs in full, but the first drive counts as a CD (the `jne` after `cmp eax, 5` becomes NOPs) and the `_findfirst` counts as found (`test eax, eax` → `xor eax, eax`).
   - **Lesson:** the first version jumped from the start of the loop straight to the "found" path. At 0x62a680 (injury history, `injury.cpp`) that path uses `esi` as 0, and what zeroes `esi` is the loop itself (0x62a6f8). With the jump, the object was built with garbage and the game crashed later, when loading the data for a new game (0x62d471). Rule: in a hook, do not skip code whose side effect the rest of the routine uses; prefer changing only the result. Two other copies, tied to `auto_setup.cfg`, only show "CD Not Required" when the CD is present; they were left as they are.
2. **Folder.** `WinMain` opens `HKLM\Software\Sports Interactive Ltd\Championship Manager 01-02` requesting **full access** (`KEY_ALL_ACCESS`) and does a `chdir` to the `Location` value. Without administrator rights Windows denies it, the `chdir` does not happen and, outside the game folder, it stops at `Langlib.cpp 479` (the old "registry error"). Fix: `chdir` to the exe's own folder (`GetModuleFileNameA`).
3. **`game.cfg`.** Stores the absolute path of the user folder. If the old folder still exists, the saves go there. Fix: the stored path is ignored and the game folder always applies.

Tested without the ISO mounted and with the game opened from another folder; with the CD fix above, Lucas started a season and saved the game without errors.

## 3a. Native resolution (`engenharia-reversa/resolucao.py`)

The screen layout is fixed in the exe. `CM0102Patcher` mapped out how to change it; the tool reads the data from `referencias/CM0102Patcher` (it does not copy it):
1. patch `to1280x800` (192 chunks: prepares the exe for larger screens and changes the background names to `Data\bkg1280_800.rgn`, `Data\g800.mbr`, `Data\m800.mbr`);
2. patch `tapanispacemaker` (5 chunks);
3. width/height constants (74) and 11 layout values calibrated per resolution (`ResolutionChanger.cs`; they exist for 720×480 up to 1920×1080).

Before writing, it checks that each chunk still has the original 3.9.68 bytes (none collides with the portable exe fixes). The images are converted preserving each file's color format (the `.rgn` files are RGB565; the side-bar `.mbr` files are **RGB555**), with a center crop so as not to distort.

**1920×1080 works** (`cm0102-1080.exe`): Lucas started a season and saved. The interface elements keep their 2001 pixel size; the higher resolution gives more usable area, not bigger letters.

Pending: the background photos (`Pictures\`) live in a single folder, and each resolution needs its own. For now the game runs with background switching turned off in the settings; the idea is for the video layer to fit the photo to the resolution by itself.

## 4. Video and the screen "flicker"

- The game's drawing is entirely in **16 bits per pixel** (RGB565).
**Original** behavior (without our `ddraw.dll`):

- **Windowed DirectDraw:** `SetCooperativeLevel(DDSCL_NORMAL)` followed by `SetDisplayMode(desktop_width, height, 16)` (0x5e2a53–0x5e2a83). On Windows 11 the desktop stays at 32 bits (the mode is emulated), but the call triggers a display reconfiguration (`WM_DISPLAYCHANGE`) on opening and another on closing: that is the flicker. Without this call, the surfaces stay at 32 bits and the game draws wrongly (swapped colors, squashed image). Tested.
- **Fullscreen DirectDraw:** real 800×600×16 (exclusive `SetDisplayMode`); the flicker is unavoidable on this path.
- **Windowed GDI:** builds the image in memory and copies it with `StretchDIBits`, which converts to any color depth. **No display reconfiguration** (measured with `engenharia-reversa/escuta_tela.py`). Cosmetic detail: a white strip is left over at the bottom of the window.
- **Fullscreen GDI:** `ChangeDisplaySettingsA` to 800×600×16; it also flickers.

### Actual use of DirectDraw (surveyed with the spy, `CM_ESPIAO=1`)

| Method | Use |
|---|---|
| `DirectDrawCreate`, `SetCooperativeLevel` | windowed: `DDSCL_NORMAL` (0x8); fullscreen: `EXCLUSIVE|FULLSCREEN|ALLOWREBOOT` (0x13) |
| `SetDisplayMode` | windowed: (desktop width, height, 16); fullscreen: (800, 600, 16) |
| `CreateSurface` ×2 | primary (`caps 0x200`) and 800×600 frame in system memory (`caps 0x840`) |
| `GetSurfaceDesc` (primary) | reads the pixel format: RGB565 |
| `CreateClipper`, `SetHWnd`, `SetClipper` | windowed only |
| `Lock`/`Unlock` (frame) | the game draws the pixels by itself; with a rectangle, the pointer points to its corner |
| `Blt` with `COLORFILL` (frame) | paints areas with one color (`DDBLTFX.dwFillColor`, offset 0x50) |
| `Blt` frame → primary | presentation; destination in screen coordinates |

Apart from that, the window procedure calls `USER32!ChangeDisplaySettingsA` directly when gaining/losing focus in fullscreen.

### Own video layer (`rust/`, `jogo/ddraw.dll`)

The exe imports `DirectDrawCreate` from `ddraw.dll`, and Windows looks for the DLL first in the exe's folder (`ddraw.dll` is not a KnownDLL). Our `ddraw.dll` implements only what is above:
- the frame is our own buffer; `SetDisplayMode` is ignored (**the Windows mode never changes**);
- presentation converts RGB565 → 32 bits (bit replication) and draws to the window with `StretchDIBits`: 1:1 windowed, proportional scaling with black bars in fullscreen (the game window already covers the whole screen);
- in fullscreen, mouse messages are converted back to 800×600 coordinates (subclass of the window procedure);
- `ChangeDisplaySettingsA` is hooked in the exe's IAT (first hook in the executable) and does nothing.

Windowed, the window is **resizable** (border and maximize): the frame follows with proportional scaling and the mouse is converted. Scaling: nearest neighbor at an integer factor; our own **area-average downscaling** (`cm0102-base/src/reducao.rs`, integer weights, only the changed region is recomputed; ~18 ms for the whole 1920×1080 frame to 1583×890) when the window is smaller than the frame; Windows HALFTONE for upscaling at a fractional factor. `CM_REDUCAO=windows` switches downscaling back to HALFTONE, for comparison. The chosen size and position (end of dragging or moving, maximize/restore) are kept in `jogo/janela.cfg` (`largura altura maximizada x y`) and are reapplied on opening and whenever the game restarts the video. This happens when entering "Start New Game" and when saving, when the game itself returns the window to its native size, in the center of the screen.

Measured with `escuta_tela.py`: no display reconfiguration windowed, in fullscreen, or when switching between the two. Applies only to `cm0102.exe`/`cm0102-portatil.exe`; the GDI version does not use DirectDraw.
